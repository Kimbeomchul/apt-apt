# 집의 기준 — 서울·경기 아파트 구매 의사결정 서비스 기획서

작성일: 2026-09-16 / 버전: 0.1 / 상태: 초기 조사 및 구현 기획

## 1. 서비스 목표

“내 연봉과 모은 돈으로 서울·경기에서 어떤 아파트를 살 수 있으며, 그 선택이 생활에 얼마나 부담되는가?”에 답한다.

서울특별시·경기도의 **400세대 이상 아파트**를 대상으로, 단지별 평가와 전용 59㎡·84㎡ 가격, 개인별 대출 추정, 월 상환 부담을 한 화면에서 비교한다. 서비스명은 가칭이다. 사용자가 요청한 ‘깃에 웹사이트 배포’는 GitHub 저장소 및 GitHub Pages 공개 배포를 기본안으로 해석한다.

이 문서는 구현 가능한 기획서다. 실제 서울·경기 전체 단지를 수집·평가한 결과표나 은행의 대출 승인 결과가 아니다. 현재 작업 폴더에는 기존 서비스나 Git 저장소가 없다.

## 2. 초기 시장 조사와 서비스 방향

| 비교 대상 | 공개 화면에서 확인한 중심 기능 | 우리 서비스에 적용할 방향 |
|---|---|---|
| 네이버페이 부동산 | 매매·임대 매물 탐색 및 외부 제공 부동산 정보 | 실제 매물 확인 링크로 연결 |
| 호갱노노 | 실거래가, 세대수·평형 필터, 학원가·거래량·출근 등 주변 정보 | 평가 항목의 근거를 사용자가 확인할 수 있도록 설계 |
| KB부동산 | 시세·실거래가·분양 정보 | 실거래가와 금융기관 담보평가용 가격을 구별 |

이는 공개 웹 화면을 통한 초기 기능 조사이며, 전체 경쟁 기능이나 이용자 수를 조사한 결과는 아니다. 사업 가설은 **단지 평가 → 개인별 자금 계산 → 살 수 있는 후보 비교**의 흐름을 간결하게 만드는 데 있다. 경쟁 서비스에 같은 기능이 없다고 단정하지 않는다.

출처: [네이버페이 부동산](https://land.naver.com/), [호갱노노](https://www.hogengnono.com/recommend/apt), [KB부동산](https://kbland.kr/).

시장 현황은 출시 전 실거래 데이터를 집계해 별도 리포트로 만든다. 서울·경기/시군구/59·84㎡별 거래 건수, 3·6·12개월 가격 변화, 거래 공백, 가격 분포를 표시한다. 서로 다른 단지의 거래 비중 변화가 가격 상승처럼 보일 수 있으므로 동일 단지·면적 비교를 우선한다. 현재 조사만으로 지역별 상승률이나 저평가 단지를 확정하지 않는다.

## 3. 분석 범위와 평형 기준

- 포함: 서울·경기 소재, 단지 총세대수 400 이상, 매매 가능한 아파트. 400세대는 포함한다.
- 주상복합은 아파트 부분을 확인하여 포함하고 유형을 표시한다. 오피스텔·빌라·분양권·입주권·순수 임대단지는 초기 매매 추천에서 제외한다.
- 혼합 단지는 전체 세대수와 분양 세대수를 구별하고 매매 가능한 주택만 추천한다.
- 주소·공식 단지 식별자를 기준으로 동명이인 단지를 구별한다. 여러 단지를 임의로 합쳐 400세대로 만들지 않는다.
- 세대수가 확인되지 않거나 자료끼리 충돌하면 확인 대기 상태로 둔다.
- 기본 평형: **전용 59㎡급(통상 공급 24~25평형), 전용 84㎡급(통상 공급 33~34평형)**. 단지별 공급면적이 다르므로 24평=전용 24평으로 계산하지 않는다.
- 면적 그룹은 우선 58~60㎡, 83~85㎡로 탐색하되 실제 타입·면적을 확인하여 연결한다. 해당 타입이 없으면 ‘해당 평형 없음’으로 표시하며 비례 환산 가격을 만들지 않는다.

전체 대상 단지 수는 원천 데이터 수집 후 확정한다. 화면에 대상 수, 분석 완료 수, 자료 부족 수를 함께 표시한다.

실제 확보가 확인된 데이터는 [한국부동산원 단지 식별정보](https://www.data.go.kr/data/15106861/fileData.do)와 [국토부 실거래가 API](https://www.data.go.kr/data/15126468/openapi.do)다. API 이용 신청·키 발급, 이용량, 필드 및 라이선스는 연동 단계에서 확인한다. 후보 출처의 전 필드가 확보됐다고 가정하지 않는다.

네이버는 게시 정보의 체계적 무단 복제·배포 등을 제한한다. 초기 서비스에서 네이버 매물을 자동 수집하여 재게시하지 않는다. 검증된 단지 링크를 제공하고, 직접 연결이 확인되지 않으면 검색 안내를 제공한다. 실시간 호가 도입은 별도 데이터 이용 권한 확보 후 진행한다. [네이버 부동산 안내](https://land.naver.com/)

### 가격 표시 원칙

1. 대표값: 같은 단지·면적 그룹의 최근 90일 유효 거래 중위값. 5건 미만이면 180일로 확장하고 확장 사실을 표시한다.
2. 180일에도 5건 미만이면 ‘소표본 참고가격’, 12개월간 유효 거래가 없으면 ‘최근 거래 없음’으로 표시한다. 이 기준은 서비스 설계값이며 검증 후 조정한다.
3. 함께 표시: 최신 개별 실거래, 거래일·층·정확한 전용면적, 표본 수, 관측 최저·최고가, 데이터 수집 시각.
4. 거래 취소 건은 대표값에서 제외한다. 직거래는 별도 표시하고 중개거래 대표값과 분리한다. 이상치는 삭제 전에 사유를 기록하며 자동으로 허위 거래라고 판단하지 않는다.
5. 동일 면적이라도 타입·층·향·수리 상태에 따라 가격이 달라진다. 중위값을 특정 매물의 현재 구매 가격으로 표현하지 않는다.
6. 대출 계산에는 사용자가 입력한 예상 계약가를 우선 사용한다. 담보평가액은 별도 입력 또는 확인 가능한 자료를 사용하고, 미확인 시 가정을 명시한다.

거래 신고에는 계약 후 시차가 있으므로 최근 거래량은 잠정치다. 법상 신고기한은 계약 체결일부터 30일 이내다. [부동산거래신고법 제3조](https://www.law.go.kr/LSW/lsLinkCommonInfo.do?chrClsCd=010202&lsJoLnkSeq=1027900007)

## 5. 급지 평가 방식

급지는 정부 공인 등급이 아닌 **본 서비스의 공개된 평가 모델**이다. 입지 등급, 단지 품질, 가격 매력도를 각각 표시한다. 비싼 아파트라는 이유만으로 좋은 주거환경 점수를 주지 않는다.

### 입지 점수: 100점

| 항목 | 제안 배점 | 평가 근거 |
|---|---:|---|
| 일자리 접근성 | 30 | 주요 업무지구까지 출근 시간, 환승 수; 사용자 직장은 개인 맞춤 점수로 별도 반영 |
| 대중교통 | 20 | 실제 도보 접근성, 노선·배차·환승 편의 |
| 교육 환경 | 20 | 학교 접근·통학 안전·학원 인프라; 공식 통학구역 확인 |
| 생활 인프라 | 15 | 병원·마트·공원·문화시설 접근 |
| 주거 환경 | 10 | 소음·경사·공개된 환경 및 재해 관련 자료 |
| 수요·거래 안정성 | 5 | 거래 지속성 및 표본 규모 |

초안 기준: 1급지 85점 이상, 2급지 75~85점 미만, 3급지 65~75점 미만, 4급지 55~65점 미만, 5급지 55점 미만. 이는 확정된 지역 서열이 아니다. 지표별 정규화 기준과 표본을 검증한 뒤 등급을 발행한다. 서울·경기 공통 기준과 지역 내 백분위를 함께 제공한다.

### 단지 품질 점수: 100점

| 항목 | 제안 배점 | 확인 사항 |
|---|---:|---|
| 건물·주거 구조 | 25 | 준공연도, 구조, 동간 거리, 공개된 보수 정보 |
| 주차·보행 편의 | 20 | 세대당 주차, 지상 차량 동선, 경사, 승강기 접근 |
| 관리 상태·비용 | 20 | 관리비 비교, 유지관리 자료, 자료 확인 범위 |
| 커뮤니티 시설 | 20 | 헬스장·수영장·골프·독서실·돌봄·게스트하우스 등 실제 운영 여부 |
| 배치·녹지·생활 편의 | 15 | 조경·놀이터·단지 내 이동·택배 등 |

커뮤니티 시설은 개수뿐 아니라 운영 시간, 별도 비용, 세대수 대비 규모, 최근 확인일을 보여준다. 정보가 없는 경우 ‘없음’으로 처리하지 않는다. 익명 후기의 하자·소음 주장은 검증된 건물 결함으로 표시하지 않는다.

가격 매력도는 유사 입지·연식·면적의 비교군 대비 가격 차이와 자체 과거 거래 범위로 설명한다. 향후 상승을 보장하는 투자 점수로 만들지 않는다. 재건축은 단계·출처·추정 분담금 확인 여부를 별도 표시하고, 사업 기대감을 현재 주거 품질에 가산하지 않는다.

결측 항목을 0점으로 채우지 않는다. 필수 지표와 가중치 기준 80% 이상 확보 시에만 잠정 종합점수를 발행하고, 확인된 항목에 대한 점수와 데이터 충족률을 병기한다. 80% 기준도 검증 대상이다. 원시값→정규화→가중합을 재현할 수 있도록 평가 버전을 보관한다.

정책 레코드에는 발표일, 시행일, 종료일, 검증일, 출처, 지역 코드, 적용 대상, 예외, 계약·신청·실행일 경과조건, 검토 상태를 저장한다. 발표 예정 정책은 시행 중 정책과 분리한다. 검증되지 않은 케이스는 ‘추가 확인 필요’로 반환한다.

| 자산 | 예금·현금, 매도할 금융자산의 예상 순현금, 전세보증금, 반환 예정일, 기존주택 처분 순유입액 |

| 주택·가구 조건 | 나이, 세대 주택 수, 생애최초 여부, 혼인·자녀 조건, 기존주택 처분 여부 |

처음에는 연봉·현금·기존 대출 유무만 받아 대략적인 범위를 보여주고, 상세 조건을 채울수록 계산 정확도를 높인다. 누락된 부채를 자동으로 0원으로 취급하지 않으며 빠른 계산에 사용한 가정을 보여준다. 배우자 소득 합산은 상품·차주 조건을 확인하고 배우자 부채도 반영한다.

## 8. 자금·대출 계산 엔진

계산 순서는 자격 확인 → 적용 정책 선택 → 기존 부채 상환액 산정 → 대출 제약별 한도 → 구매 부대비용 → 월 현금흐름이다.

```text
DSR상 신규 연간 상환여력 = max(0, 인정 연소득 × 적용 DSR 비율 − 기존 부채의 규정상 연간 원리금)
추정 주담대 = min(LTV 한도, DSR 한도, 적용 시 DTI 한도, 정책 절대한도, 상품 한도)
가용 자기자금 = 잔금일까지 확보되는 순현금 − 선상환 부채 − 유지할 비상금
총 필요자금 = 계약가격 + 취득 관련 세금 + 중개보수 + 등기 등 비용 + 이사·수리 예산
추가 필요현금 = max(0, 총 필요자금 − 가용 자기자금 − 추정 주담대)
월 잔여자금 = 월 실수령액 − 기존 대출 실제 납입액 − 신규 대출 납입액 − 생활·주거비
```

기존 부채의 규정상 DSR 원리금은 단순한 실제 월 납입액×12와 다를 수 있다. 대출 종류·만기·상환 방식별 규정으로 계산하고, 현금흐름에는 실제 납입액을 사용한다. 스트레스 금리는 한도 심사용이며 실제 월 납입액의 약정금리와 구별한다.

원리금균등 상품의 원금 역산은 월 상환 가능액 A, 심사용 월 금리 r, 개월 수 n에 대해 P=A×(1−(1+r)^(-n))/r로 계산한다. 금리 0은 별도 처리한다. 다른 상환 방식은 별도 모듈을 사용한다.

전세보증금은 반환 시점과 전세대출 상환액을 차감하여 순액으로 계산한다. 기존 집 처분대금도 담보대출·처분비용 차감 후 반영한다. 기존 부채를 상환하는 시나리오는 현금과 DSR에서 각각 올바르게 반영하고 중복 차감하지 않는다. 계약금·중도금·잔금 시점별 자금 부족도 표시한다.

집값에 따라 LTV·세금·절대한도가 달라지므로 단순히 ‘현금+연봉 배수’로 최대 구매가를 계산하지 않는다. 특히 15억·25억 같은 경계에서 한도가 불연속적으로 바뀔 수 있으므로 전체 구간에 단일 이분탐색을 적용하지 않고 정책 구간별 가능 범위를 계산한다. 실제 단지 후보도 개별 가격으로 재계산한다.

### 결과는 세 가지로 제공

- **안정 구매:** 사용자가 정한 비상금과 월 상환 한도를 유지하며, 금리 +2%p·소득 감소 시나리오도 확인.
- **최대 구매(영끌):** 명시적으로 투입하기로 한 자산과 제도상 추정 한도를 사용. 비상금 해제는 사용자 선택으로 하고 자동 가정하지 않음.
- **추가 자금 필요:** 부족한 현금, 월 상환 초과액, 정책상 미충족 조건을 구별.

카드에 LTV 한도·DSR 한도·정책 한도와 최종 제한 요인을 표시한다. 신용대출을 더하면 무조건 구매력이 커진다고 가정하지 않는다. 기존 부채 감소 또는 증가에 따른 주담대 재계산과 주택 취득 제한 확인이 필요하다. 화면에는 ‘추정치 · 금융기관 심사에 따라 달라짐’을 짧게 표시한다.

## 10. 기술 구조와 GitHub 배포

제안 구조: React·TypeScript·Vite 정적 프런트엔드 + Python 데이터 수집/정제 + 버전별 JSON 데이터 + GitHub Actions + GitHub Pages.

```text
공공데이터 API/공식 파일
  → Actions에서 수집·정제·400세대 필터·품질 점검
  → 지역별 단지/거래요약/평가 JSON + 검증된 정책 JSON
  → 정적 사이트 빌드·Pages 배포
  → 브라우저에서 사용자 재무 계산·후보 검색
```

GitHub Pages는 정적 웹사이트 배포 방식이므로 수집 작업은 Actions에서 실행한다. API 비밀키는 Actions Secrets에 보관하고 빌드 결과·공개 JSON·로그에 넣지 않는다. [GitHub Actions 안내](https://github.github.com/workshops/actions-for-dev/index.html), [Secrets 사용 문서](https://docs.github.com/en/actions/how-tos/write-workflows/choose-what-workflows-do/use-secrets)

재무 입력은 기본적으로 브라우저 메모리에서만 처리한다. 저장은 사용자가 선택했을 때만 로컬에 보관하고 삭제 기능을 제공한다. URL·분석 이벤트·공개 저장소에 연봉·자산·부채를 넣지 않는다. 초기에는 로그인·서버 저장·실시간 게시판을 제외한다. 사용자가 말한 커뮤니티는 우선 단지 시설과 거주 후기 조사로 반영한다.

실거래는 일 단위 갱신을 목표로 하되 최근 구간 재수집과 정기 과거 대조로 취소·정정 거래를 반영한다. 정책은 자동 검색만으로 즉시 적용하지 않고 검증 후 배포한다. 갱신 실패 시 마지막 정상 자료와 실패 시점을 표시한다. 지도는 이용약관·공개 배포 권한·키 제한·호출 비용 확인 후 추가하고 목록 탐색은 독립적으로 동작하게 한다.

수천 단지의 상세 데이터는 지역별로 나누어 로딩한다. 정적 배포에서 직접 단지 URL 접속이 실패하지 않도록 라우팅을 구성한다. 초기 운영비는 데이터·지도 라이선스 및 계정별 Actions/Pages 이용 조건 확인 후 산정한다.
